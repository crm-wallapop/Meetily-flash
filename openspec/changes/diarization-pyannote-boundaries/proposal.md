## Why

The companion change `diarization-speaker-split-persistence` makes the per-speaker split persist correctly — but on `meeting-cde5c264-…` it yields only a **2-way split** of the 26.8 s evidence window, not the per-turn resolution the transcript text implies. The diarization emits boundaries only where the uniform chunk grid (`SPLIT_TARGET_SECS = 3.0`, `FINE_SPLIT_SECS = 2.0`) changes AHC label, so rapid back-and-forth *within* one grid cell is collapsed into a single run. Storage persistence is necessary but not sufficient; the complaint is not resolved until there are more boundaries.

The boundary source already exists, empirically validated. `pyannote-segmentation.onnx` (~5.8 MB, on disk at `~/.meetily-models/`) provides ~16.9 ms-resolution change-points. Phase 2/2b probes confirmed: the 5.7–32.5 s banter window — which the chunk grid collapses to **1 boundary at 21.36 s** — produces **24 turns at pyannote-default smoothing**. The premise that pyannote provides finer boundaries than the chunk grid is empirically verified; the open question was *how to deliver those boundaries given the runtime conflict*, now resolved by removing the conflicting runtime (Option 1).

## What Changes

Port nemo_titanet embedding extraction from sherpa-onnx to the `ort` crate, and run the whole app on one ORT runtime. The port is the validated `embed-probe-ort/src/main.rs` logic (knf-equivalent fbank + CMVN, now bug-fixed with the `f32::EPSILON` log floor), lifted into a `NemoEmbeddingExtractor` struct in the speaker module (`frontend/src-tauri/src/audio/speaker/`). The I/O contract is the verified nemo_titanet model contract: input `audio_signal float32[N,80,T]` + `length int64[N]` → output `embs float32[N,192]`.

With sherpa gone, the two-ORT conflict is resolved at the root: pyannote-segmentation-3.0 loads via a **second in-process `ort::Session`** in the same process (no subprocess, no IPC, no second binary) — the exact pattern the Phase 1 probe (`pyannote_ort_probe.rs:48-59`) validated. The diarization flow becomes:

1. Load pyannote boundaries: slide a 10s window at 1s step over the 16kHz mono samples, decode per-frame powerset logits to 3-speaker multilabel activity via hysteresis at onset 0.5, apply pyannote-default smoothing (median rad=3, min_on=0.3s, max_off=0.5s — the only Phase 2b config that hit BOTH anchors), emit change-points.
2. **INTERSECT** the pyannote change-points with the Whisper `transcript_segments` (`fetch_transcript_timestamps`): a pyannote change-point inside a Whisper speech region becomes an intra-region split; silence regions between Whisper segments are preserved as silence (NOT embedded). Pyannote AUGMENTS the Whisper boundaries; it does not supersede them.
3. Pass the intersected set as `transcript_segments` to `process()`. `build_chunks` sub-divides each Whisper speech region by the pyannote boundaries INSTEAD OF its own `effective_split` uniform grid (D4 removes `effective_split`).
4. Extract embeddings via the ported nemo_titanet `ort::Session`, then the existing AHC + cap + temporal-coherence smoothing + `refine_pass2` + registry pipeline runs UNCHANGED on the intersected sub-segments.

Three structural points drive the design (all surfaced by the panel and verified against the codebase + the ported code):

1. **The downstream pipeline is already runtime-agnostic.** Meetily's label-quality machinery (`cluster_by_centroids`, `smooth_to_fixed_point`, `refine_pass2`, the cap, the registry) is pure Rust over `Vec<f32>` embeddings. Only the embedding extraction (`sherpa_adapter.rs:17-82` `SherpaOnnxEmbeddingAdapter`) and the registry's backing store (`sherpa_adapter.rs:1297-1362` `SherpaOnnxRegistryAdapter` wrapping sherpa's `SpeakerEmbeddingManager`) touch sherpa types. The port surface is small and mechanical — the fbank + CMVN + pad-16 + transpose + transpose + session-builder code already exists, validated, in `embed-probe-ort/src/main.rs`.
2. **One runtime, no process boundary, no permanent tax.** With sherpa removed, Parakeet + nemo_titanet + pyannote all share one `ort 2.0.0-rc.10` runtime — no conflict by construction (the conflict was only ever sherpa's bundled ORT vs the `ort` crate). No subprocess, no IPC contract, no second signed binary, no per-release signing tax, no updater version-skew, no Windows Defender stall → silent-fallback. (Contrast Option 3, panel-rejected on permanent subprocess debt once the port proved viable.)
3. **Labels are structurally absent.** The pyannote `ort::Session` is over pyannote-segmentation-3.0 only (the powerset segmentation model); it emits per-frame speaker-activity, not speaker *labels*. Meetily's AHC + cap + smoothing + `refine_pass2` + registry remain authoritative for labeling, exactly as today. This is stronger than "sherpa labels discarded": there is no labeling pass to discard.

**Out of scope:** a subprocess/IPC contract/second signed binary (the panel-rejected Option 3 path); changing the AHC threshold, cap logic, or temporal smoothing (these stay tuned to nemo_titanet embeddings; the 0.9946–0.9989 fidelity is within their operating margin); re-training or re-exporting nemo_titanet (the on-disk model is used as-is, only the loader changes).
